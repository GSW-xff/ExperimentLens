# ExperimentLens 互联网大厂 HR 面试问答手册

> 适用场景：互联网大厂 AI Agent、后端、平台工程、机器学习工程与研发实习岗位的 HR 面试、主管面和综合面。
>
> 使用原则：所有回答都要和真实经历一致。仓库能证明项目具备什么能力，但不能证明某位候选人独立完成了全部能力。

## 1 阅读方法与核心结论

HR 面试不会像技术面那样连续追问代码实现，但会借项目判断候选人的动机、贡献、可信度、沟通能力、复盘能力、执行力和岗位匹配度。回答时要把技术事实翻译成业务问题、个人动作和可验证结果，不要只背 FastAPI、Agent、SSE、Lease 等名词。

建议先记住一条主线：ExperimentLens 解决机器学习实验结果分散、人工排查慢、Agent 结论缺少证据、长任务执行不稳定的问题。系统把结果表、配置和日志标准化，用确定性统计生成异常发现，再让受限 Agent 调用六个项目级只读工具查证。最终结论必须绑定 EvidenceRef。工程上采用 API 与 Worker 分离、持久化步骤、Lease、heartbeat、fencing token、SSE 断线续传、Trace 和真实运行评测。

回答任何项目题时，优先使用下面的四句结构：

1. 先说场景和问题，让非技术面试官知道为什么值得做。
2. 再说自己的职责边界，明确哪些是我负责、哪些是团队或已有基础。
3. 选择一到两个关键动作，解释判断、取舍和协作过程。
4. 用数据或交付物收尾，同时说明数据的适用边界。

项目当前可以核验的结果包括：30 条真实 AgentRun 离线评测全部通过，无效证据率为 0，工具参数有效率与超时恢复率为 100%；本地 SQLite 和确定性离线模型条件下，100 个可靠性任务全部完成，重复 ToolCall、事件丢失和 SSE 重放失败均为 0，注入一次 Worker 崩溃后恢复耗时约 224 毫秒。这些数字是本地基线，不代表互联网生产 SLO，也不能外推为真实大模型线上效果。

## 3 先确定你的真实贡献口径

仓库反映项目能力，不等于个人贡献记录。回答前先从下面三种口径中选择最符合自己的版本，并把括号内容替换成真实事实。

### 3.1 接手维护口径

适用于主要完成项目理解、运行复现、文档、测试、修复和后续迭代的候选人。

> 我接手了 ExperimentLens，系统梳理了数据导入、确定性分析、Agent 工具循环和 Worker 恢复链路。我复现了评测与故障注入实验，补充了相关文档和测试，并负责了后续的具体迭代。面试中我会把已有架构和我亲自完成的改动分开说明。

### 3.2 模块负责口径

适用于真实负责一个或多个模块的候选人。

> 项目由多人或多个阶段共同完成，我主要负责的是（填写模块）。我承担了需求拆解、实现、测试和验证，并和（填写协作者）对齐接口。其他模块我能够解释整体链路，但不会说成是我独立实现的。

### 3.3 独立项目口径

只有在能解释核心代码、提交记录、取舍和失败过程时使用。

> 我从实验排查这个问题出发独立搭建了主要版本，完成了从数据标准化、确定性分析到 Agent 工具循环、持久化执行和评测的闭环。为了证明系统可靠，我还设计了真实运行评测与故障注入实验。具体成果和限制都能在仓库测试及报告中复现。

建议准备一张个人贡献清单，至少写清楚需求来源、自己改过的文件、做过的关键决定、遇到的失败、测试方法和对应 commit。若回答中使用“设计了”“主导了”“从零实现了”，必须能接受至少三轮追问。

## 4 开场介绍与项目陈述

### 4.1 请你做一下自我介绍

**考察意图**  HR 想确认你的经历主线、求职方向、表达能力和岗位匹配度，不需要听完整简历复述。

**回答结构**  当前身份与方向，最相关的两段证据，为什么投递这个岗位。控制在 60 到 90 秒。

**参考回答**

> 您好，我目前主要关注 AI Agent 与后端工程。我最近重点学习和维护的项目是 ExperimentLens，它面向机器学习实验诊断，把结果表、配置和日志统一起来，再让 Agent 通过受限工具完成证据化分析。我在这个过程中重点理解并实践了 Agent 工具调用、持久化任务、故障恢复、评测和测试。项目目前有 30 条真实运行评测和 100 任务故障注入基线。我希望应聘（岗位名称），因为这个岗位既要求理解 AI 应用，也重视可靠工程和快速学习，这与我最近形成的能力主线比较一致。

**容易失分**  超过两分钟；从高中开始讲；罗列十几个技术名词；没有说明为什么适合当前岗位；把项目全部能力都说成个人独立完成。

### 4.2 请用三十秒介绍这个项目

> ExperimentLens 是一个机器学习实验诊断 Agent。它把多次实验的结果、配置和日志统一管理，先用确定性统计找异常，再由 Agent 调用六个只读工具查证原因。最终结论必须绑定真实证据。项目还实现了任务崩溃恢复、实时进度、可观测性和自动评测，重点解决 Agent 容易编造、长任务不稳定和升级后难以判断是否退化的问题。

### 4.3 请用一分钟介绍这个项目

> 机器学习工程师常常需要比较几十次实验，人工看表和搜日志很慢，也容易把随机波动误判成真实提升。ExperimentLens 先把 CSV、Excel、配置和日志标准化为 run、指标、参数和产物，再用确定性统计计算组间差异、波动和异常。Agent 不直接凭 Prompt 猜结论，而是调用六个当前项目内的只读工具，并要求答案引用真实 EvidenceRef。工程上，API 只负责创建任务，独立 Worker 通过 Lease 领取并从持久化步骤恢复；浏览器通过 SSE 接收可重放事件。当前离线评测是 30 条全部通过，100 个本地可靠性任务全部完成。我的具体贡献是（填写真实贡献），其他部分我能从整体架构角度说明。

### 4.4 请用三分钟完整介绍

三分钟回答要覆盖五点：问题、用户、方案、个人贡献、结果与边界。推荐节奏是四十秒讲问题，一分钟讲主链路，一分钟讲个人行动与难点，二十秒讲结果和限制。

> 这个项目服务机器学习工程师和 AI 平台研发。用户做完多轮实验后，通常需要手工对表、比配置、搜日志，既耗时，也容易因为单个 seed 或异常 run 得出错误结论。我们的目标不是做通用聊天机器人，而是做一个可追溯的实验诊断工作流。
>
> 系统将结果表、配置和日志标准化，用确定性程序计算关键统计，再让 Agent 根据问题选择只读工具。模型只能读取当前项目，工具输入输出有 Schema 校验，最终回答必须通过 EvidenceRef 校验。为了让长任务可恢复，API 与 Worker 分离，任务步骤、事件和工具调用写入数据库；Worker 通过带版本的 Lease 领取任务，崩溃后由新 Worker 接管。前端通过 SSE 展示过程并支持断线续传。
>
> 我主要负责（填写真实范围）。最难的是（选择一个真实难点），因为（说明具体约束）。我做了（两项关键动作），并通过（测试或实验）验证。最终（填写个人交付），项目基线显示 30 条真实运行评测通过，100 个本地任务在故障注入后完成且没有重复工具调用和事件丢失。这些数字来自 SQLite 与离线模型环境，我不会把它说成线上规模结果。

### 4.5 为什么这个项目值得放在简历上

> 它不是只展示一次对话效果，而是覆盖了从数据处理、确定性分析、工具调用到持久化执行、证据校验、可观测性和评测的完整链路。对我来说，价值不只是用了大模型，而是训练了我把一个不稳定的 AI 能力变成可测试、可解释、可恢复系统的思路。简历上我只会写自己真正完成并能现场复现的部分。

## 5 项目动机与业务价值问题

### 5.1 为什么选择做 ExperimentLens

**考察意图**  判断项目是否来自真实问题，以及你有没有主动思考。

**参考回答**

> 我选择这个方向，是因为实验分析既有明确用户痛点，也适合验证 Agent 的工程价值。实验数据里有结构化指标、配置和日志，既不能完全交给大模型自由推理，也不能只靠固定规则覆盖所有问题。这使得“确定性计算加受限 Agent”成为合理组合。我希望通过这个项目学习的不只是模型调用，而是证据、权限、恢复和评测这些真正影响可用性的环节。

**追问准备**  为什么不做通用聊天机器人；你在哪里见过这个问题；如果没有用户访谈，如何验证需求。没有真实用户调研时，应说这是基于典型研发流程和样例数据验证的工程项目，不要声称已经服务大量企业客户。

### 5.2 它解决了什么具体问题

> 它解决三类问题。第一，实验材料分散，人工比较运行结果、配置和日志效率低。第二，平均指标变好不一定代表方案真的更好，可能被单个 seed、失败 run 或数据版本差异影响。第三，普通 Agent 可能编造数字，任务失败后也难恢复。项目通过标准化数据、确定性统计、只读工具、证据校验和可恢复 Worker，把诊断过程变得更可追溯。

回答时不要说“提高了研发效率百分之多少”，除非你做过用户测试并有原始记录。当前仓库能证明的是系统测试与可靠性基线，不能证明真实团队节省的工时。

### 5.3 目标用户是谁

> 当前首要用户是需要比较多次训练或评测结果的算法工程师、研究人员和 AI 平台研发。他们关心哪个方案更稳定、异常来自哪里、下一轮最小验证实验是什么。第二类用户是技术负责人，他们需要可分享、可追溯的结论。当前项目更适合个人或小团队的实验诊断演示，还没有完成企业级多租户权限、组织管理和真实生产容量验证。

### 5.4 用户为什么不用 Excel 或脚本

> 少量固定格式的数据，用 Excel 或一次性脚本就够了。ExperimentLens 的价值出现在数据源多、分析问题会变化、需要跨指标配置日志查证，并且需要保留过程和证据时。它把重复的数据整理和排查步骤固化下来，再让 Agent按问题选择工具。这个项目不是替代所有脚本，而是给复杂、反复发生的诊断任务一个统一入口。

### 5.5 用户为什么不用普通大模型

> 直接把表格和日志塞给模型有上下文、成本、计算准确性和权限风险。ExperimentLens 让程序计算关键数字，模型只能通过有类型的只读工具获取需要的信息，答案引用真实 EvidenceRef。这样可以降低模型把数字看错、访问其他项目或编造证据的风险。这里应该说“降低风险”，不能说“彻底消除幻觉”。

### 5.6 项目的核心竞争力是什么

> 核心不是模型参数或界面，而是证据化诊断链路。关键数字来自确定性计算，Agent 行为受工具和项目边界限制，回答必须通过证据校验，整个运行过程还能被持久化、恢复和评测。这使它比一次性 Prompt 演示更容易复现和回归验证。当前差异化仍主要是工程设计，尚未经过真实商业化和大规模用户验证。

### 5.7 项目如何产生业务价值

> 预期价值是缩短实验排查时间、减少错误结论并提高复现效率。要把预期价值变成真实业务价值，还需要做用户试点，记录从问题提出到定位原因的时间、人工操作次数、诊断采纳率和错误归因率。当前项目已经准备了可追溯分析与评测基础，但没有真实 ROI 数据，所以我会把它称为经过工程验证的原型，而不是成熟商业产品。

### 5.8 如果只能保留一个功能你会保留什么

> 我会保留证据驱动的诊断主链路，也就是确定性分析、受限工具和 EvidenceRef 校验。界面、更多连接器甚至模型都可以替换，但如果结论不能回到真实实验数据，这个产品就失去了可信度。这个选择也体现了项目把可靠性放在功能数量之前。

## 6 个人贡献与主人翁意识问题

### 6.1 你在项目中的角色是什么

**回答模板**

> 我的角色是（独立开发者 模块负责人 接手维护者）。我直接负责（列出两到三项可核验工作），交付物包括（代码 测试 文档 基线报告）。我参与理解但不是主要负责人的是（范围）。这样划分是为了让面试官准确判断我的能力，也方便继续追问我真正做过的部分。

不要用“我们做了”回避个人贡献，也不要把团队结果全部变成“我做了”。最好的回答同时包含个人动作和协作接口。

### 6.2 你具体写了哪些代码

只列能打开仓库现场解释的内容。建议按照“文件或模块、解决的问题、验证方式”回答。

> 我主要修改了（文件路径或模块），解决（具体问题）。例如（说明一个函数或数据流），对应测试是（测试文件或命令），最后通过（结果）验证。我还负责（第二项）。对于 Worker、评测或前端中不是我实现的部分，我能解释接口，但不会归入个人贡献。

### 6.3 哪个决策最能体现你的判断

> 我最认可的判断是没有让大模型直接计算关键统计，而是保留确定性分析，再让 Agent 做工具选择和解释。原因是平均值、置信区间和异常检测需要稳定复现，而自然语言模型更适合处理开放问题和组织结论。代价是需要维护工具 Schema 和证据映射，但换来了可测试性。若这个决策并非我最初提出，我会说我在接手后理解、验证并延续了这项设计。

### 6.4 你做了哪些超出任务要求的事情

选择真实例子，可从补充测试、基线、文档、自动化脚本、边界说明中挑一个。

> 完成功能后，我发现只展示一次成功对话不足以证明系统可靠，所以补充了（真实行动）。我把它变成自动化测试或可复现报告，并记录环境和限制。这样后续修改 Prompt、模型或 Worker 时，不需要靠人工印象判断是否退化。

### 6.5 如果没有你 项目会少什么

> 如果没有我，项目仍然有（承认已有基础），但会缺少（你的独特交付）。我带来的主要增量是（具体产物或决策），它让（可观察结果）。我不会说整个项目离不开我，更希望用可验证增量说明价值。

### 6.6 你如何证明自己真正理解项目

> 我能从用户上传文件开始，顺着标准化、确定性分析、创建 AgentRun、Worker 领取、工具调用、证据校验、事件重放一直讲到评测采集；也能运行演示、定位测试失败，并解释为什么选择 Lease、幂等键和 SSE。更重要的是，我能指出当前没有完成 Temporal、多租户权限和生产容量验证，而不是只背成功路径。

### 6.7 你最有成就感的部分是什么

> 我最有成就感的不是界面能输出答案，而是把“看起来能用”变成“可以被验证”。当一次 Worker 崩溃后，任务能由另一个 Worker 接管，工具调用不重复，事件序号连续，并且这些行为由自动化测试和报告证明时，我更确定这个系统具备工程价值。若这部分不是我的个人实现，应改为“我最认可并重点复现的部分”。

### 6.8 如何描述团队协作

> 我们按边界协作：数据与分析模块输出稳定领域对象，Agent 模块只通过 Repository 和工具接口访问，前端依赖 API 与 SSE 契约。我负责（真实范围），在接口变化前先对齐输入输出和失败语义，再补测试。出现分歧时，我们回到用户场景、风险和验证成本，而不是只比较技术偏好。

## 7 技术难点与解决过程问题

### 7.1 项目最难的地方是什么

推荐选“可恢复 Agent 执行”或“证据约束”，不要同时展开五个难点。

> 我认为最难的是保证 Agent 长任务在故障后安全恢复。只把任务状态改成 running 不够，因为 Worker 可能崩溃、暂停后又恢复，重复执行工具也会造成不一致。项目把模型、工具和证据边界保存为 AgentStep，用有期限 Lease 与 heartbeat 判断执行者是否存活，用 fencing token 拒绝旧 Worker 提交，再用幂等键避免相同逻辑工具调用重复写入。我们通过三个崩溃点和 100 任务故障注入验证了这条链路。

### 7.2 你遇到过什么具体问题

回答必须是你真实遇到的。建议使用“现象、定位、修复、回归”四步。

> 现象是（测试失败或异常行为）。我先用（日志 Trace 数据库记录或最小复现）缩小范围，发现根因是（具体原因），而不是表面上的（容易误判点）。我修改了（代码或配置），又补了（测试），最后运行（验证命令）确认旧场景和新场景都通过。这个过程让我学会先建立可复现证据，再改代码。

### 7.3 为什么 API 和 Worker 要分离

> Agent 任务包含模型和工具调用，耗时和失败都不确定。如果在请求线程里执行，接口容易超时，服务重启也会丢失上下文。API 只创建并持久化任务，Worker 异步领取，让控制面保持轻量，也给重试、恢复和扩容留下边界。代价是需要处理任务状态、事件一致性和 Worker 竞争，所以项目加入了 Lease、Step 持久化和幂等键。

### 7.4 为什么需要 fencing token

> Lease 到期后新 Worker 可以接管，但旧 Worker 可能只是网络暂停，恢复后仍然提交结果。fencing token 是每次领取递增的版本号，关键写入前都校验当前版本，只允许最新持有者提交。它解决的是“旧执行者复活”问题，而不只是普通的重复任务。

### 7.5 如何降低 Agent 幻觉

> 项目做了四层约束。关键统计由确定性代码计算；模型只能调用注册过的只读工具；参数和结果经过 Schema 校验；最终答案必须引用并通过 EvidenceValidator 检查的 EvidenceRef。评测还检查无效证据、跨项目访问、未授权写入和 Prompt Injection。它能降低事实错误和越权风险，但自然语言推理仍可能有偏差，因此还需要真实模型评测与人工抽检。

### 7.6 为什么用 SSE 而不是 WebSocket

> 当前需求主要是服务端向浏览器推送任务进度，客户端的操作仍走普通 HTTP，所以 SSE 更简单，也原生支持事件 ID 和断线续传。每个 AgentEvent 有单调 sequence，客户端带 Last Event ID 后可以从数据库继续读取。若未来需要高频双向交互或实时协作，再考虑 WebSocket。

### 7.7 为什么没有直接使用大型 Agent 框架

> 项目的核心问题是状态、证据、隔离和恢复，不是快速组合很多工具。最小化自研 Orchestrator 更容易精确控制 AgentStep、幂等键、Trace 和失败语义。代价是要自己维护更多基础能力。未来如果工作流显著复杂，可以评估框架，但仍应保留领域接口、证据校验和持久化边界。

### 7.8 为什么同时有 Flask 和 FastAPI

> 项目保留了已有 Flask 业务接口，通过适配器挂到 FastAPI 下，新控制面和 Agent 接口使用 FastAPI。这样可以在不一次性重写稳定功能的情况下逐步演进。缺点是技术栈暂时重复，需要清晰划分路由和生命周期。等迁移收益足够明确，再分阶段收敛。

### 7.9 SQLite 和 PostgreSQL 怎么选择

> SQLite 适合本地演示、测试和单机环境，部署成本低；PostgreSQL 更适合多 Worker 和生产并发。项目通过 SQLAlchemy 与 Alembic 保留切换路径，但当前公开性能数字来自本地 SQLite。选择数据库应根据并发、故障模型和运维成本，而不是为了简历堆技术。

### 7.10 如果流量增长十倍你先做什么

> 我不会先给一个未经测量的架构答案。第一步是区分瓶颈在模型、工具、数据库还是事件读取，并补充队列等待、Agent 时长、工具耗时、数据库连接和错误率指标。随后优先把 SQLite 切到 PostgreSQL，验证索引和领取竞争，再根据压测决定是否引入专用消息队列、Outbox Publisher 或水平扩展 Worker。任何容量数字都要来自可复现实验。

## 9 协作 沟通与冲突问题

### 9.1 你如何向非技术同学解释项目

> 我会说它像一个只看授权档案的实验侦探。程序先把实验成绩、配置和日志整理好，Agent 决定查哪份档案，但不能随意修改，也不能在没有证据时下结论。这样既利用了 AI 处理开放问题的能力，也保留了数字计算和证据核对的确定性。

### 9.2 如何和产品经理对齐需求

### 9.3 技术方案有分歧怎么办

> 我先确认双方争论的是目标、风险还是实现偏好。比如是否引入 Temporal，应该比较现有任务规模、故障场景、团队维护成本和迁移收益。当前项目规模下，数据库 Lease 与持久化 Step 已能验证核心语义，所以先保持简单；当跨服务工作流、长周期审批和重试复杂度上升时再引入。用约束和实验做决定，比用资历压结论更有效。

### 9.4 接口变更如何避免影响别人

> 先写清 API 或事件契约，保留兼容路径，再同时更新服务测试、前端类型和文档。像 AgentEvent sequence、SSE 重放和工具 Schema 都属于跨模块契约，改动时要做回归。提交中应把功能、测试和迁移放在一起，让协作者能够复现。

### 9.5 如何处理别人代码中的问题

> 我先建立最小复现和证据，再说明影响范围，不直接评价个人。提出修改时给出测试或监控依据，也尊重原方案当时的约束。如果问题跨越职责边界，我会先同步相关负责人，避免未经沟通的大范围重写。

### 9.6 你如何汇报进度

> 我会按“已完成、证据、风险、下一步”汇报。例如：Worker 三个崩溃点已恢复，相关集成测试通过；当前风险是基线只覆盖 SQLite 与离线模型；下一步补真实模型评测。这样比说“基本完成百分之八十”更容易让负责人判断。

### 9.7 遇到需求变化怎么办

> 先判断变化是否影响核心目标和已有契约，再估算修改范围。对于 ExperimentLens，如果从离线分析增加外部写操作，我不会把它当成普通新工具，而会重新设计审批、权限、审计和幂等边界。把变化对应的风险说清楚，再和负责人调整优先级。

## 15 可直接复用的 STAR 素材

### 15.1 故障恢复素材

**Situation**  Agent 任务包含模型和工具调用，Worker 崩溃可能导致任务卡住、重复工具调用或事件不连续。

**Task**  让任务在进程异常后能够被新 Worker 接管，并保证旧 Worker 不覆盖新结果。

**Action**  持久化 AgentStep；用 Lease 和 heartbeat 管理任务所有权；用 fencing token 拒绝过期执行者；用幂等键保护工具调用；在模型结果、工具执行和证据校验三个边界注入崩溃。

**Result**  三个崩溃点均恢复为 completed；100 任务本地基线全部完成，重复 ToolCall 和事件丢失为 0。若你只是复现而非实现，应把 Action 改为“我复现并验证了”。

### 15.2 证据约束素材

**Situation**  普通 Agent 可能把指标看错、引用不存在的 run，或被日志中的恶意文本影响。

**Task**  让实验诊断结论可追溯，并限制模型的数据访问和工具权限。

**Action**  关键统计交给确定性代码；仅开放六个项目级只读工具；用 Pydantic 校验参数；把工具返回映射为 EvidenceRef；最终答案通过 EvidenceValidator；评测覆盖跨项目、未授权写入和 Prompt Injection。

**Result**  当前 30 条离线真实运行评测全部通过，无效证据率为 0。限制是评测规模小且使用确定性模型。

### 15.3 渐进式架构演进素材

**Situation**  项目已有 Flask 业务接口，同时需要 FastAPI 控制面和新的异步 Agent 能力。

**Task**  在不一次性重写稳定功能的情况下演进架构。

**Action**  保留原有领域分析和 Flask 兼容接口，通过适配器挂载到 FastAPI；新功能依赖 Repository 接口；用 Alembic 管理数据库变化；为前后端契约补测试。

**Result**  原有 API 契约与工作区兼容，新控制面、Worker 和评测可以逐步接入。代价是过渡期存在双框架维护成本。

### 15.4 接手陌生项目素材

**Situation**  项目同时包含 React、Python 服务、数据库、Agent、评测和部署文件，直接逐文件阅读效率低。

**Task**  在较短时间内建立全局理解并完成可验证改动。

**Action**  先运行测试和演示，再沿用户主链路追踪数据；画出模块与接口；选择一个小改动完成代码、测试、文档和 commit；通过故障测试验证理解。

**Result**  能独立讲清主链路、定位问题并维护指定模块。请把 Result 替换为你的真实交付和时间。

## 21 一页速记

**一句话定位**  ExperimentLens 是一个证据驱动的机器学习实验诊断 Agent，用确定性分析、受限只读工具和 EvidenceRef 让诊断结果可追溯。

**核心用户问题**  实验多、材料散、人工排查慢、随机波动容易误判、普通 Agent 可能编造、长任务失败难恢复。
