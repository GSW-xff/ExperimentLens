# ExperimentLens 实验结果分析与排错 Agent 使用说明书

## 1. 产品简介

ExperimentLens 是一套面向机器学习、数据科学和其他计算实验的本地分析工作台。它把分散的结果表、实验配置和运行日志整理成统一的 runs，通过确定性统计和异常检测生成可追溯的分析结论，再给出排错假设、下一轮最小验证实验和可编辑报告。

它适合回答以下问题：

- 候选配置是否稳定优于 baseline，而不是偶然取得更高分？
- 哪些 seed、运行或日志导致结果波动或失败？
- 当前结论依赖哪些原始记录？
- 下一轮如果只能进行少量实验，应该优先验证什么？
- 如何把本轮实验整理成一份可以保存和分享的分析报告？

ExperimentLens 不会修改用户代码，也不会直接启动实验。用户始终负责确认字段、选择 baseline、判断是否采纳假设以及执行后续实验。

## 2. 开始使用

### 2.1 启动应用

首次安装请在项目目录中执行：

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
pnpm install
./scripts/start_local.sh
```

浏览器访问：

```text
http://127.0.0.1:5050
```

该脚本同时启动 API 和独立 Agent Worker。应用默认只监听本机地址。第一次打开且工作区为空时，系统会自动创建“Transformer 调参实验”示例项目，用户可以先用它了解各个分析页面。

### 2.2 推荐使用流程

```text
准备实验文件
    ↓
新建分析并填写目标
    ↓
一次性导入结果、配置和日志
    ↓
确认 Run ID、实验组、主指标与 Baseline
    ↓
查看总览、Runs 和异常证据
    ↓
检查排错假设并向 Agent 追问
    ↓
选择下一轮最小验证实验
    ↓
编辑并下载分析报告
```

## 3. 用户需要准备什么文件

每个分析至少需要一个实验结果表。配置和日志不是必需文件，但缺少它们会减少 Agent 可以使用的排错证据。

建议在一次导入中同时选择同一批实验的所有文件，并确保不同文件中的 `run_id` 一致。

### 3.1 实验结果表：必需

支持格式：

- CSV：`.csv`
- TSV：`.tsv`
- Excel：`.xlsx`、`.xls`
- JSON：`.json`
- JSON Lines：`.jsonl`

每一行表示一次实验运行。至少需要以下三类字段：

| 信息 | 是否必需 | 推荐列名 | 说明 |
|---|---|---|---|
| 运行标识 | 必需 | `run_id` | 每次运行的唯一 ID，不能重复 |
| 实验组 | 必需 | `group` | 配置组、模型组或对照组名称 |
| 主指标 | 必需 | `accuracy`、`f1`、`loss` 等 | 用于选出最佳运行和比较 baseline |
| 随机种子 | 强烈建议 | `seed` | 用于判断多 seed 稳定性 |
| 运行状态 | 建议 | `status` | 如 `completed`、`failed`、`oom` |
| 运行耗时 | 建议 | `duration_seconds` | 单位建议统一为秒 |
| 其他指标 | 可选 | `train_loss`、`val_loss`、`memory_gb` | 用于补充比较和排错 |
| 实验参数 | 可选 | `batch_size`、`learning_rate` | 可直接放在结果表中 |
| 数据或代码版本 | 建议 | `dataset_version`、`code_version` | 用于检查实验可比性 |

推荐 CSV 示例：

```csv
run_id,group,seed,status,accuracy,train_loss,duration_seconds,batch_size,learning_rate,dataset_version
base-17,Baseline,17,completed,0.842,0.382,3520,32,0.0003,v3
base-29,Baseline,29,completed,0.848,0.371,3490,32,0.0003,v3
cos-17,Cosine LR,17,completed,0.865,0.341,3690,32,0.0003,v3
cos-29,Cosine LR,29,failed,,,1810,32,0.0003,v3
```

注意事项：

- `run_id` 应在本批数据内保持唯一。
- 同一列必须使用一致的单位。例如，不要在 `duration_seconds` 中混用秒和分钟。
- 失败运行也应保留一行，并把 `status` 写为 `failed`、`error`、`crashed` 或 `oom`。
- 缺失数值请留空，不要使用 `-`、`unknown` 等字符串伪装成数值。
- 比较多 seed 时，尽量让每个实验组使用相同的一组 seed。

### 3.2 JSON 结果表示例

JSON 结果可以是记录数组，也可以把记录数组放在 `runs`、`results`、`experiments`、`trials` 或 `data` 字段中。

```json
{
  "runs": [
    {
      "run_id": "base-17",
      "group": "Baseline",
      "seed": 17,
      "status": "completed",
      "accuracy": 0.842
    },
    {
      "run_id": "candidate-17",
      "group": "Candidate",
      "seed": 17,
      "status": "completed",
      "accuracy": 0.861
    }
  ]
}
```

### 3.3 实验配置：推荐

支持格式：

- JSON：`.json`
- YAML：`.yaml`、`.yml`

每份配置必须包含与结果表一致的 `run_id`、`run` 或 `trial_id`，这样系统才能把配置关联到对应运行。嵌套配置会被展开为点号字段，例如 `optimizer.lr`。

YAML 示例：

```yaml
run_id: cos-17
model: resnet50
dataset_version: v3
batch_size: 32
optimizer:
  name: adamw
  lr: 0.0003
  weight_decay: 0.01
training:
  epochs: 40
  precision: bf16
```

如果所有配置字段已经包含在结果表中，可以不再单独上传配置文件。

### 3.4 运行日志：推荐

支持格式：

- 纯文本：`.txt`、`.log`
- JSON Lines：`.jsonl`

系统会逐行保留日志证据，并优先通过以下方式关联 run：

1. 日志文件名中包含完整 `run_id`，例如 `cos-17.log`。
2. 日志内容中包含完整 `run_id`。
3. 日志中存在 `run=...`、`run_id=...` 或 `trial=...` 形式的标识。

日志示例：

```text
2026-09-17 09:14:02 run=cos-29 epoch=1 train_loss=1.292
2026-09-17 09:35:18 run=cos-29 warning: validation accuracy oscillation detected
2026-09-17 09:36:07 run=cos-29 RuntimeError: CUDA out of memory
```

MVP 会重点识别：

- OOM 或显存不足；
- NaN、Inf、overflow 等数值异常；
- traceback、exception、error、failed 等运行错误。

日志中的 token、密码、连接串和个人信息应在导入前删除或脱敏。

### 3.5 文件限制与导入建议

- 单个文件不能超过 50 MB。
- 建议一次选择同一分析批次的全部结果、配置和日志。
- 不要导入可执行文件、模型权重或与分析无关的大型二进制文件。
- 同一批实验若来自不同数据版本或代码版本，应明确保留版本字段，而不是手工改成相同值。
- 原始文件会原样保存在本地工作区，标准化过程不会覆盖源文件。

## 4. 在 ExperimentLens 中进行一次完整分析

### 4.1 创建分析项目

1. 点击页面右上角的“新建分析”。
2. 填写“项目名称”，例如“Transformer 学习率实验”。
3. 在“实验目标”中写清本轮希望验证的问题，例如：

   > 在训练耗时增加不超过 10% 的条件下，判断 Cosine LR 是否稳定提高验证集 accuracy。

4. 点击“继续导入文件”。

一个好的实验目标最好包含主指标、比较对象和约束条件，这会让后续报告更容易理解。

### 4.2 导入文件

1. 在导入区域选择结果表、配置和日志文件。
2. 检查下方文件列表是否完整。
3. 点击“识别实验结构”。

建议一次选择多个文件。结果表负责建立 runs，配置和日志负责补充证据。

### 4.3 确认字段映射

系统识别完成后会显示以下字段：

- `Run ID 列`：唯一标识一次运行的列。
- `实验组列`：区分 baseline 和候选配置的列。
- `Seed 列`：随机种子列，可以留空，但会降低稳定性分析质量。
- `状态列`：成功、失败或未完成状态。
- `主指标`：本轮最重要的评价指标。
- `Baseline 组`：作为对照的实验组名称，必须与数据中的值完全一致。
- `指标方向`：选择“越高越好”或“越低越好”。
- `耗时列`：用于比较运行成本。

确认原则：

- accuracy、F1、AUC、BLEU 一般选择“越高越好”。
- loss、error、perplexity、latency 一般选择“越低越好”。
- Baseline 应是当前已接受的方案，而不一定是本批数据中得分最低的方案。
- 如果识别结果错误，直接修改输入框中的列名或组名。

点击“确认并开始分析”后，系统会生成标准化 runs、统计汇总、异常、假设和实验建议。

## 5. 如何阅读分析结果

### 5.1 实验总览

“实验总览”是完成一次分析后首先查看的页面。

页面内容包括：

- **证据摘要**：当前最重要的总体结论。
- **有效运行**：成功运行数与总运行数。
- **最佳 Run**：主指标最优的单次运行。它不等同于最优实验组。
- **Baseline 差异**：候选组均值相对 baseline 的变化。
- **优先异常**：需要先处理的严重或警告级发现数量。
- **组间图表**：各组主指标均值的直观比较。
- **候选组可信度**：均值变化、效应量和 95% 置信区间。

判断建议：

- 均值更高不代表一定更好。若置信区间跨过 0，应把结论视为证据不足。
- 单个最佳 Run 不能代替组间稳定性判断。
- 出现失败或无效指标时，应先处理异常，再决定是否采用候选配置。
- 小样本提示意味着需要谨慎解释，通常应补充更多 seed。

### 5.2 Runs 对比

“Runs 对比”展示每次运行的：

- Run ID；
- 所属实验组；
- seed；
- 运行状态；
- 主指标；
- 耗时；
- 关键配置。

可以使用页面搜索框按 run ID、实验组、seed 或状态筛选。排查异常时，先在异常证据中找到 run ID，再回到此页比较它与同组其他 runs 的配置和结果。

### 5.3 异常与证据

每条 Finding 都包含：

- 严重程度：`critical`、`warning` 或 `info`；
- 异常标题和判断依据；
- 置信度；
- 具体 run、指标、配置或日志行引用；
- 产生该结论的检测器和版本。

推荐处理顺序：

1. 先处理 `critical`，例如运行失败、主指标无效和 OOM。
2. 再处理 `warning`，例如组内离群点、seed 波动或数据版本不一致。
3. 最后检查 `info`，例如 seed 缺失。

异常页面只陈述确定性发现，不把相关性自动解释为因果关系。

### 5.4 排错假设

“排错假设”由多个 Findings 综合而来。每个假设包含：

- 假设内容；
- 支持证据；
- 当前不确定性；
- 置信度；
- 最小验证方法。

置信度表示当前证据对该解释的支持程度，不表示因果关系已经得到证明。如果页面显示“当前没有足够证据支持明确的故障原因”，应优先补充 seed、训练曲线、资源日志或版本信息，而不是强行选择某个原因。

### 5.5 下一轮实验

“下一轮实验”页面把高优先级假设转化为可执行方案。每个方案会明确：

- 唯一主要变量；
- 推荐 seed；
- 必须保持不变的条件；
- 预期观察；
- 不同结果应如何解读；
- 优先级与大致成本。

MVP 只负责提出方案，不会自动改代码或启动运行。用户应把方案转写到自己的实验配置或任务系统中，执行完后再把新结果作为新的分析批次导入。

## 6. 如何向 Agent 追问

在桌面端点击右上角“追问 Agent”打开对话面板。Agent 会继承当前项目的 runs、主指标、baseline、Findings、Hypotheses 和 Proposals 上下文。

适合的提问方式：

- “为什么 Cosine LR 均值更高，但仍需要更多实验？”
- “哪几个 runs 导致 Large Batch 的方差增大？”
- “如果只能再跑三次，应该怎样安排 seed？”
- “显存不足这个假设依赖哪些日志证据？”
- “当前结论是否受到数据版本不一致影响？”
- “哪个候选组在性能和运行时间之间更平衡？”

回答中出现的证据标签可以对应到 run、指标或日志行。Agent 回答的依据是当前项目已经保存的确定性分析结果；如果证据不足，它应明确说明缺少什么数据。

不推荐的提问方式：

- 与当前实验无关的一般知识问题；
- 要求 Agent 猜测未导入的训练过程；
- 要求 Agent 自动修改代码或直接启动实验；
- 没有说明约束条件的“下一步做什么”。

如果答案过于笼统，可以补充限制，例如“总预算只能增加 3 次训练”“不能改变数据集”“优先排查 OOM”。

## 7. 生成、编辑与下载报告

1. 打开“分析报告”。
2. 系统根据当前保存的分析结果生成报告，包含目标、组间统计、异常、证据、假设和下一轮实验。
3. 在报告编辑区域补充研究背景、决策理由或团队备注。
4. 编辑内容会在短暂延迟后自动保存到本地工作区。
5. 点击“下载当前报告”。

如果报告未经手工编辑，默认下载生成的 Markdown 报告；发生手工编辑后，下载当前保存的 HTML 报告。

报告中的结论和统计值来自当前已保存的分析结果。更新输入数据后，应重新创建或运行分析，再生成新版报告。

## 8. 常见场景示例

### 8.1 候选组均值更高，但置信区间跨过 0

含义：当前观察到正向变化，但运行数量或稳定性不足，无法排除随机波动。

建议操作：

1. 查看候选组是否存在离群 seed。
2. 检查每组是否使用相同 seed。
3. 在“下一轮实验”中采用补充 seed 的方案。
4. 不要只引用单个最佳 Run 作为结论。

### 8.2 某个 Run 失败且日志出现 OOM

含义：资源峰值可能导致运行失败，缺失结果也可能改变组均值。

建议操作：

1. 在“异常与证据”中确认日志行和 run ID。
2. 在“Runs 对比”中核对失败运行的 batch size 和其他配置。
3. 固定代码、数据、seed 和评估方式，只降低 batch size 复跑。
4. 同时记录峰值显存，判断 OOM 假设是否得到支持。

### 8.3 同一组不同 seed 波动很大

含义：配置可能对初始化或数据顺序敏感，均值提升的可复现性不足。

建议操作：

1. 找到偏离组中位数的 runs。
2. 检查异常运行是否有配置、数据版本或日志差异。
3. 使用预先指定的 seed 补充运行，避免只选择有利 seed。
4. 同时比较均值、标准差、置信区间和最差运行。

### 8.4 数据版本不一致

含义：组间差异可能来自数据，而不是实验配置。

建议操作：

1. 不要直接解释为模型或超参数带来的提升。
2. 把 baseline 和候选组固定到同一数据版本。
3. 使用相同 seed 进行配对复跑。
4. 在报告限制条件中保留本次数据不一致说明。

## 9. 常见问题与故障处理

### 9.1 提示“未找到包含实验结果的表格”

检查是否至少导入了一个 CSV、TSV、Excel 或结构化 JSON/JSONL 文件，并确认文件中存在多行实验记录。只有 YAML 或日志不能建立 runs。

### 9.2 提示“未识别到数值指标列”

检查指标列是否为纯数值，是否使用了 `%`、`N/A`、`unknown` 等文本。建议把百分比统一转换为 0 到 1 的小数或统一的数值百分比。

### 9.3 Baseline 为空或对比结果缺失

检查“Baseline 组”是否与结果表中的组名完全一致，包括大小写和空格；同时确认 baseline 至少有一个有效主指标。

### 9.4 配置没有关联到 Run

确认配置文件中包含 `run_id`、`run` 或 `trial_id`，并且值与结果表完全一致。只把 run ID 写在配置文件名中还不足以建立配置关联。

### 9.5 日志没有出现在证据中

确认日志文件名或内容包含完整 run ID，并检查错误文本是否包含 OOM、NaN、Inf、traceback、exception、error 或 failed 等可识别信号。

### 9.6 Agent 表示“尚不能判断”

这不是系统错误，而是当前证据不足。根据不确定性提示补充多 seed 结果、训练曲线、资源日志、数据版本或代码版本，然后创建新的分析批次。

### 9.7 页面无法访问

确认终端中的 `experimentlens-api` 和 `experimentlens-worker` 进程仍在运行，并访问 `http://127.0.0.1:5050`。AgentRun 长时间保持 `pending` 通常表示 Worker 未启动，或 API 和 Worker 没有使用同一个数据库。如果端口被占用，可以设置 `EXPERIMENTLENS_PORT` 后重新启动。

## 10. 数据保存与隐私

默认工作区位于：

```text
.experimentlens/workspace/<project_id>/
```

主要内容包括：

```text
sources/original/       原始上传文件
normalized/             标准化 runs、metrics 和 params
analysis/               汇总、异常、假设和实验建议
reports/                Markdown 或 HTML 报告
scratch/                字段识别过程中的临时结构化数据
```

- 原始文件默认只保存在运行 ExperimentLens 的本机。
- 标准化数据使用 Parquet，分析结果使用 JSON，报告使用 Markdown 或 HTML。
- 当前 MVP 没有账号系统和云端同步。
- 不要在日志中保留密码、访问令牌、数据库连接串或个人敏感信息。
- 如果未来配置外部模型服务，应先确认组织的数据出境和隐私要求。

## 11. 当前 MVP 的能力边界

当前版本不包含：

- 自动修改用户代码或直接启动实验；
- 自动超参数搜索；
- 复杂因果推断；
- 实时训练监控；
- 多人协作和统一身份认证；
- MLflow、Weights & Biases 或 TensorBoard 的在线连接；
- 模型权重、图像等大型产物分析。

当前统计比较适用于中小规模实验结果的快速判断。对于论文结论、高风险生产决策或复杂实验设计，应由具备相关领域知识的人员复核统计假设、数据质量和实验协议。

## 12. 一页式检查清单

导入前：

- [ ] 每个 Run 都有唯一 `run_id`。
- [ ] 每个实验组使用清晰且一致的 `group` 名称。
- [ ] 主指标是数值列，单位一致。
- [ ] 多 seed 实验保留了 `seed`。
- [ ] 失败运行保留状态和日志。
- [ ] 配置、结果和日志使用相同 run ID。
